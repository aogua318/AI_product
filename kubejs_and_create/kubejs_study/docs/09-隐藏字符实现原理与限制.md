# 09 - "隐藏字符"的实现原理与限制

对应示例：[chat_miao.js](../server_scripts/chat_miao.js)（喵化聊天，
配套语言文件在 [assets/lang](../assets/kubejs/lang/zh_cn.json)）。

## 需求

1. 玩家公屏发言结尾没有"喵"就补一个，有就不动
2. 这个"喵"**不能被外部工具或文本搜索搜到**

## 为什么不能用常规手段"隐藏"

| 方案 | 为什么不行 |
|------|-----------|
| 前后夹零宽字符（U+200B） | 只能骗过"搜索整个词组"，搜单字"喵"照样命中——字符本身还在文本里 |
| 用形近字/生僻字替代 | Unicode 里没有和"喵"几乎一样的字，玩家一眼就能看出不对 |
| 转义/编码后发送 | 客户端没有解码逻辑就显示不出来 |

关键认识：**只要字符以"喵"的字面量出现在任何一层文本里（网络包、日志、聊天记录），搜得到就是没藏住。** 所以唯一干净的思路是让"喵"根本不以字符形式传输。

## 实际方案：翻译键（translatable component）

Minecraft 的文本组件支持 `translate` 类型：传输的不是文字，而是一个**键名**，
客户端显示时用自己加载的语言文件把键翻译成文字。原版物品名就是这么工作的
（日志里只有 `item.minecraft.stone`，屏幕上显示"石头"）。

于是：

**脚本侧**（`server_scripts/chat_miao.js`）：

```js
PlayerEvents.chat(event => {
    if (event.message.trimEnd().endsWith('喵')) return
    const comp = event.component
    comp.append(Text.translate('chat.kubejs.miao'))  // 追加键，不是字
    event.setComponent(comp)
})
```

**资源侧**（`assets/kubejs/lang/zh_cn.json`，KubeJS 会把 `kubejs/assets`
整个当作客户端资源包加载，见 `KubeJSResourcePackFinder`）：

```json
{ "chat.kubejs.miao": "喵" }
```

## 数据流

```
玩家发送 "你好"
    │  （ServerChatEvent → KubeJS PlayerEvents.chat）
    ▼
服务端广播的组件: [{text:"你好"}, {translate:"chat.kubejs.miao"}]
    │  ← 此处及之前，"喵"字不存在，日志/抓包都只有键名
    ▼
客户端渲染时查语言文件: chat.kubejs.miao → "喵"
    ▼
屏幕上显示: 你好喵
```

相关源码位置：
- 事件：`player/PlayerChatReceivedKubeEvent.java`（`getComponent` / `setComponent` 包装 NeoForge 的 `ServerChatEvent`）
- 事件接线：`KubeJSPlayerEventHandler.chatReceived`（取消/修改组件走 NeoForge 标准管线）
- `Text.translate`：`plugin/builtin/wrapper/TextWrapper.java:251`
- 资源包：`kubejs/assets` 由 `client/KubeJSResourcePackFinder.java` 挂载

## 为什么 en_us.json 也要写

原版语言加载有回退机制：当前语言缺键时回退到 `en_us`。
所以只要 `en_us.json` 里有这个键，**任何语言**的客户端都能正常显示"喵"；
都不存在时才会原样显示键名 `chat.kubejs.miao`（不美观，但依然搜不到"喵"）。

## 第 2 版修正：源码也要去字面量化

初版脚本里 `endsWith('喵')` 和注释都写着这个字的字面量——对**源码文件**做搜索照样现形。
第 2 版的修正思路是"全程只和码点数字打交道"：

| 位置 | 初版（有字面量） | 第 2 版（无字面量） |
|------|-----------------|--------------------|
| 结尾判断 | `text.endsWith('喵')` | `text.codePointAt(text.length - 1) === 0x55B5` —— 取结尾字符的码点数字比较 |
| 语言文件的值 | `"喵"` | `"\u55B5"` —— JSON unicode 转义，解析后才变成该字 |
| 注释 | 直接写"喵" | 只称"M 字 / 码点 0x55B5"，不写真字 |

两个用到的 API（学习点）：
- `text.codePointAt(i)`：取第 i 个字符的 Unicode 码点数字。与 `charCodeAt` 的区别是能正确处理增补平面字符（码点 > 0xFFFF 的字，如 emoji）
- JSON 的 `\uXXXX` 转义：标准 JSON 语法，Minecraft/Gson 解析语言文件时会解码成真字，但对原始文件的文本搜索只能搜到 `55B5` 这个十六进制串

修正后已验证：`kubejs_study/` 下所有"喵"字面量只出现在**注释和说明文字**里，
可执行代码（字符串、比较值、语言文件的键值）零匹配——用 grep 排除注释行确认。

最终约定（按用户要求）：
- **可执行代码里不能出现"喵"字面量**——码点比较、JSON `\u55B5` 转义就是为了这个
- **注释和说明文字里可以写"喵"**——注释是给人看的解释，不影响隐藏效果
  （搜索"喵"的人会命中注释，但那只能看到方案说明，聊天文本里依然没有"喵"）

注意：**本文档（docs/）的字面量不受限**——学习文档必须写它才能把机制讲清楚。

## FAQ：直接在输入末尾加 `\u55B5` 再发送行不行？

不行。`\u55B5` 是**文件层面的写法**（源码字面量/JSON 转义），不是数据的形态：
代码被加载的那一刻，转义就解码成了内存里的真字符。

- `comp.append('\u55B5')` 与 `comp.append('喵')` 在运行时完全等价。
- 服务端序列化用 Gson，非 ASCII 字符按 UTF-8 原样输出（喵 = E5 96 B5 三个字节），
  **不转义**——所以网络包 JSON 和日志里都是真字"喵"，搜得到，隐藏失败。
  转义写法只防"搜源码"（这正是码点/转义方案在源码加固里的用途），防不住"搜运行时数据"。
- 如果反过来，把 `\u55B5` 这六个 ASCII 字符当文本发送：包和日志确实搜不到喵，
  但聊天框没有转义解码逻辑，玩家屏幕上就显示 `\u55B5` 原文——功能穿帮。

三种方案对比：

| 方案 | 屏幕 | 网络包/日志 |
|------|------|------------|
| 直接 append 喵（或 `\u55B5` 解码后） | 喵 | **喵，搜得到** |
| 发送字面文本 `\u55B5` | `\u55B5`，穿帮 | 搜不到 |
| **翻译键 `chat.kubejs.miao`**（现行方案） | 喵 | 只有键名，搜不到 |

翻译键方案的不可替代性：**"喵"在服务端内存里从头就不存在**——服务器只构造键名字符串，
解码发生在每个客户端渲染时查语言文件那一刻。字符从未走过"服务端 → 网络 → 日志"这条路。

## 极简版（只防源码搜索）

如果需求降级为"只是不想让人翻文件搜'喵'找到脚本"（恶作剧场景），
翻译键 + 语言文件整套机器都**不需要**——那套东西防的是运行时数据层。
极简版整个脚本：

```js
PlayerEvents.chat(event => {
	const text = event.message.trimEnd()
	if (text.length > 0 && !text.endsWith('\u55B5')) {
		event.setComponent(event.component.append('\u55B5'))
	}
})
```

要点：
- `'\u55B5'` 加载时解码成"喵"，玩家正常看；搜文件搜"喵"搜不到（那只是 6 个 ASCII 字符）
- 不需要码点比较（`endsWith('\u55B5')` 本身就无字面量）、不需要语言文件、不需要 `.id()` 之类仪式
- **文件名和注释才是最大的暴露面**：别叫 chat_miao，别写注释——实例见 `script/server_scripts/chat_utils.js`
- 代价（也是与学习版的分界）：发送后日志/网络包里有真"喵"，防不到运行时数据层
- 与 chat_miao.js **二选一部署**，同时装会双重追加后缀

结论：方案复杂度由对抗层级决定。源码层一行转义；要防到传输层才需要翻译键全家桶。

## 诚实的限制说明

这个方案隐藏的是**原始文本层**（服务器日志、网络包 JSON、聊天记录导出文件）。
以下情况"喵"仍会以可搜索形式出现，原理上无法避免：

1. **渲染之后**：文字只要显示在屏幕上，客户端内存里就是解析后的"喵"字。
   任何对已解析文本工作的工具（游戏内聊天搜索模组、客户端聊天历史导出插件）都能搜到。
2. **OCR/截屏**：显示出来的东西永远可以被识别。
3. **玩家自己打的"喵"**：脚本对已含"喵"的消息原样放行（需求如此），
   玩家输入的"喵"是真字符，本来就在传输层里。
4. **第三方语言键导出**：有模组能把所有语言文件键值 dump 出来——键值对里存在"喵"。
   但这已经属于"翻模组资源文件"，不是文本搜索。

一句话：**在"文本可搜索"这个层面藏得干干净净；渲染层藏不住，因为要显示就无法藏。**
