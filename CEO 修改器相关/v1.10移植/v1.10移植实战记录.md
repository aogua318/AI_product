### 1.2 MCP 管道卡死的急救（已实测发生一次）

症状：`ce_ping` 反复超时；CE Lua 里 `CE_MCP.start()` 报 `Failed to create pipe: ce_mcp_bridge`。
根因：残留的 `node ce_mcp_server.js` 进程握着旧管道客户端句柄不放手，CE 端重建同名管道失败（`CE_MCP.stop()/start()`、`reloadMcpBridge()` 都救不回来）。

## 2. 复现步骤（阶段 1 完整流程）

### 步骤 1：找金钱地址（CE 常规扫描）

1. 游戏内记下当前金钱 → CE 首次扫描（类型最终确认为 **Double**；本项目游戏为 32 位进程但金额是 double，扫描时先试 4 字节整数无果时换 8 字节浮点）；
2. 花钱/赚钱 → 再次扫描过滤 → 锁定 `CEO.exe+D10C0`；
3. 存表（`CEO.CT`）。

### 步骤 2：静态定位钩点（离线，不依赖游戏运行）

1. 用 v1.02 分析报告确定语义：s00 钩"金钱结算"，跳过扣款指令；
2. 在 1.10 exe（816KB）里按字节/指令序列对照定位到 `RVA 0x2EE0D`：
   ```
   2EE0D: DD 45 08        fld  qword ptr [ebp+08]   ; 金额参数（支出为负 double）
   2EE10: 0F BE 06        movsx eax, byte ptr [esi]
   2EE13: DC 46 08        fadd qword ptr [esi+08]   ; 累加到记录
   2EE16: DD 5E 08        fstp qword ptr [esi+08]   ; 写回
   2EE19: 3B 05 xx xx xx xx  cmp eax,[x]           ; 返回点
   ```
   静态核对方法：直接读 exe 文件（.text 节 file offset ≈ RVA-0x401），用 python `struct` 解析 PE 节表后 dump 字节。
3. `[esi+8]` 与扫描出的金钱地址相差 8（D10C0-D10B8）→ 确认 esi 即金钱记录基址。

### 步骤 3：写 AA 脚本（最终版全文见 CEO_v1.10_F2.ct）

结构要点（对应 v1.02 s00"跳过扣款"语义）：

```
newmem:
  cmp esi,CEO.exe+D10B8      ; 只拦金钱记录（符号形式!见坑#1）
  jne originalcode
  fld qword ptr [ebp+08]     ; 金额
  ftst / fstsw ax / sahf     ; 判符号
  fstp st(0)                 ; 弹栈平衡
  jae originalcode           ; ≥0 收入放行
  fld [esi+08] / fstp [esi+08]  ; 支出: 原额写回
  jmp exit
originalcode:                 ; 原逻辑 fld/fadd/fstp
exit:
  movsx eax,byte ptr [esi]   ; 补回被覆盖的指令
  jmp returnhere             ; = 2EE0D+12
```

### 步骤 3.5：F2 最终 AA 脚本全文（主表内原文，逐行说明）

```asm
[ENABLE]
alloc(newmem,2048,CEO.exe+2EE0D)   ; 在钩点附近分配 2048 字节 newmem (CE 自动选合法地址)
label(returnhere)                  ; 声明三个跳转标签
label(originalcode)
label(exit)
newmem:
  cmp esi,CEO.exe+D10B8            ; ① esi=本次结算的记录基址; 只处理金钱记录(其他记录放行)
  jne originalcode                 ;    必须用符号形式! 写 4D10B8 绝对值会因重定位失效(坑#1)
  fld qword ptr [ebp+08]           ; ② 装入本次交易金额 (double, 支出为负数)
  ftst                             ; ③ 金额与 0.0 比较 (只设 FPU 状态字)
  fstsw ax                         ; ④ 状态字 → ax
  sahf                             ; ⑤ ax → CPU 标志寄存器 (FPU C0 → CF)
  fstp st(0)                       ; ⑥ 弹出金额, 恢复 FPU 栈平衡 (不弹会栈溢出)
  jae originalcode                 ; ⑦ CF=0 即金额≥0(收入) → 走原逻辑照常入账
  fld qword ptr [esi+08]           ; ⑧ 支出且开启: 读当前金额
  fstp qword ptr [esi+08]          ; ⑨ 原额写回 = 本次扣款被吞掉
  jmp exit
originalcode:
  fld qword ptr [ebp+08]           ; ⑩ 原始逻辑: 金额累加进记录再写回
  fadd qword ptr [esi+08]
  fstp qword ptr [esi+08]
exit:
  movsx eax,byte ptr [esi]         ; ⑪ 补回被跳板覆盖的原指令
  jmp returnhere                   ; ⑫ 跳回 2EE0D+12 处继续游戏代码

"CEO.exe"+2EE0D:                   ; 跳板安装点: 覆盖 fld/movsx/fadd/fstp 整 12 字节
  jmp newmem                       ; 5 字节 jmp
  nop                              ; 7 个 nop 补齐到 12 字节 (nop 数 = 覆盖长度-5)
  nop
  nop
  nop
  nop
  nop
  nop
returnhere:

[DISABLE]
"CEO.exe"+2EE0D:                   ; 还原被覆盖的 12 字节原始指令
  fld qword ptr [ebp+08]
  movsx eax,byte ptr [esi]
  fadd qword ptr [esi+08]
  fstp qword ptr [esi+08]
dealloc(newmem)
```

热键：表内该条目 `<Hotkeys>` 段 `<Action>0</Action>`（切换激活）+ `<Key>113</Key>`（F2 = 113）。金额为负的依据：步骤 2 静态对照 + 硬件断点实测（见步骤 5）。

### 步骤 4：注入与验证（MCP 工具链）

```
ce_attach_process("CEO.exe")            → 附加
ce_check_assemble(脚本)                 → 语法校验（enable/disable 各验一次）
ce_execute_lua(pcall(autoAssemble,...)) → 注入（见坑#6：优先走 Lua 通道）
ce_disassemble(钩点/newmem)             → 核对跳板与首条 cmp 的立即数是否等于本次运行真实基址
ce_read_memory("CEO.exe+D10C0","double")→ 读钱
[游戏内花钱] → 再读 → 数值不变 = 拦截成功
```

### 步骤 5：写实锤验证（定位"扣款到底走哪条路"时用）

怀疑扣款没走钩点时，挂**硬件写断点**抓现行：

```
ce_set_breakpoint("CEO.exe+D10C0", type="write", size=8)  → 32 位进程会拆成 +0/+4 两个槽
[游戏内花钱] 游戏冻结 → ce_debug_status().isBroken == true
ce_get_set_context()  → 读 RIP/寄存器（RIP=写入指令的下一条）
ce_debug_continue("run") → 放行游戏
ce_cleanup()          → 清断点
```

本次正是靠它抓到：RIP 停在钩子内 originalcode 分支的 fstp → 证明扣款走此路径、是 cmp 判断错了（见坑#1），而不是钩点选错。

- 最终脚本同步进 `v1.10CE数据\CEO_v1.10_F2.ct`（热键绑脚本条目，Action=切换激活，F2=113）；

## 3. 难点与坑点清单（每条都真实踩过）

### 坑 #1：进程基址重定位（本项目最大的坑）⚠️⚠️⚠️

**现象**：脚本语法全对、注入成功、扣款路径也确认经过钩点，但钱照扣。
**根因**：CEO.exe **每次启动都被重定位**（实测基址 0x2F0000，默认基址 0x400000 被其他 DLL 占用）。脚本里硬编码的绝对 VA `cmp esi,0x4D10B8`（= 0x400000+D10B8）与真实地址 0x3C10B8 永不相等。
**铁律**：**所有脚本/表项一律写 `CEO.exe+偏移` 符号形式，禁止任何硬编码绝对地址**。CE 会在注入时按实际基址解析。反汇编核对时也要检查 newmem 首条 cmp 的立即数 == 本次运行的真实地址（`ce_get_address("CEO.exe+D10B8")` 对照）。
**波及范围**：开发计划里已定位的 F3 钩子 `0x40A36E`、数据槽 `0x4F7048` 等全是"假设基址 0x400000"的 VA，迁移时必须换算成 `CEO.exe+A36E`、`CEO.exe+F7048`。

### 坑 #2：CE AA 不支持 `h` 后缀十六进制

`cmp esi,4D10B8h` → 汇编失败，**勾选脚本时无反应/勾不上**（CE 不给明显报错）。正确写法 `4D10B8`（CE 自动按十六进制解析含 A-F 的数字）。排查手段：`ce_check_assemble` 逐行二分。

### 坑 #3：CT 文件是 XML，脚本注释里不能有裸 `<`

注释写 `金额<0` → CE 报 `Name starts with invalid character`，整表加载失败。注释避免 `<`、`&`，或转义 `&lt;`。改完表可用 python `xml.etree` 先自检再给 CE 加载。

### 坑 #4：F2 热键绑在脚本条目上 = 切换脚本启停，不是翻转内存标志

CT 里 `<Action>0</Action>`（切换激活）作用于脚本条目时，按 F2 是注入/还原整个补丁。若脚本内部还有 `money_flag` 之类的开关变量，**没有任何东西会把它置 1**，表现为"F2 按了没反应"。定案设计：**去掉 flag 层，脚本启用即作弊，F2 直接切脚本**；不要给脚本条目再加内部开关。

### 坑 #5：旧脚本残留在游戏进程里

游戏不重启的情况下，旧版钩子会一直活着，新表改得再对也测不出效果（本次旧 flag 版脚本在后台跑了半天）。**每次换脚本版本：先恢复钩点原始字节或重启游戏进程，再注入新版**；核对钩点字节（E9 jmp 开头=有钩子，DD 45 08 开头=原始）确认当前状态。

### 坑 #6：MCP 的 `ce_auto_assemble` 偶发 `failed: nil`，Lua 通道更可靠

同一脚本 `ce_check_assemble` 通过、`ce_auto_assemble` 却报 nil。绕过：`ce_execute_lua` 里 `pcall(autoAssemble, script)`，成功率高且错误信息可读。注入后务必 `ce_disassemble` 复核。

### 坑 #7：`ce_find_what_writes` / `ce_find_what_accesses` 有监控窗口时序问题

监控期间用户来不及操作，或监控时长 ≈ MCP 工具超时（30s）导致结果丢失。对策：要么监控时长设 ≤20s 并提前让用户准备，要么改用**常驻硬件断点**（见上文复现步骤 5 的方案）——断点会一直守到事件发生，不依赖时机，实时抓现场寄存器。

### 坑 #8：游戏重启后 MCP 需要重新附加

`ce_attach_process` 的目标进程死后（重启游戏），模块枚举为空、符号解析报"无法确定 CEO.exe 的含义"。重新 attach 即可；若仍空，`ce_symbol_control(operation="load_new")` 刷新。游戏每次重启**基址可能变**，所有符号型地址自动跟随，这正是坚持坑 #1 铁律的原因。

## 阶段 2：F3 矿物修改（实战记录 2026-09-13）

### 定案

- **钩点 = `CEO.exe+A36E`**（对应 v1.02 s01 @0x409E1B，10 个钩子中唯一指令原样保留的：`mov al,[esi+03] / pop edi / cmp al,02`，6 字节补丁 jmp+nop）。
- ⚠️ 澄清：`..创业王v1.02修改器分析\v110_offset_map.json` 里 s01 的候选 "0x40976E" 是**文件偏移**（.text 节 file offset = RVA-0xC00），不是 VA，换算后即 RVA 0xA36E，与计划一致。
- **地图对象结构（实测，1.10）**：这是游戏里"地图对象"的通用头（既用于地块也用于建筑）：
  - `+0` word：对象 ID（每次读取会变的流水号）
  - `+2` byte：0xFF=无建筑的地块；0x00=有建筑
  - `+3` byte：建筑类型（实测 2=居民楼，3=矿场建筑）
  - **`+4` byte：矿物种类（实测 银=1，铝=3，另见 4、8 两种未知矿）** ← F3 写入目标 1
  - **`+6` byte：矿品质（实测 铝=84、银=98，已实测 84→99 写值生效）** ← F3 写入目标 2（用户新发现，v1.02 修改器没有）
  - **`+8` dword：储量（实测 铝=63080=0xF668、银=67850，已实测 63080→999999 写值生效）** ← F3 写入目标 3（用户新发现，v1.02 修改器没有）
  - `+16` word：疑似坐标；`+18` dword=FFFFFFFF（类似 v1.02 的无主标记）
- ⚠️ **v1.02 报告/计划里"点击地块改矿物"是转述错误**：+3 是建筑类型不是矿物。F3 正确语义 = 点击**矿场建筑**，改写它所在对象的 +4 矿物字节（v1.02 说明.txt"厂房内点击矿物修改"）。
- ~~最终实现 v4（钩子缓存方案，**已被 v5 取代**，保留作过程记录）~~：钩子缓存三个写入目标 `f3_slot`/`f3q_slot`/`f3r_slot`（自分配内存免疫重定位、无侵入，不复刻 v1.02 蹲游戏 BSS 槽 A7848 的做法）；`f3_type`/`f3q_type`/`f3r_type` 条目控制写入值。
- **最终实现 = v5 选中对象机制，见下方 [v5 定案]**（纯 Lua 零钩子，大地图选中即可改，主表采用）。

### 过程与坑

1. **复用对象缓冲噪声（本阶段最大的坑）**：钩子捕获的 esi 指向游戏**复用的临时对象池**（0x160E0xxx 区域，同一地址先后出现完全不同对象）。点一下捕获的"最后读取对象"未必是点击目标——曾把一块空地 +3 写成 2 变成"居民楼"。**对策（沿用 v1.02 经验）**：点击目标后立刻操作，或打开目标信息窗口让游戏持续读取该对象，slot 即稳定锁定（实测连续 3 次读取同地址）。
2. **字段语义靠差分实验标定**：+3/+4 的含义不是查出来的，是靠"点不同对象 → dump 对比 → 写值观察"三步实锤的。以后遇到未知结构照此办理：先拿两个已知不同的样本 diff，再写值验证，最后还原现场。
3. **F3 交互时序**：按下 F3 时写入的是"最后一次被读取的对象"，所以正确操作是"点击矿场 →（马上/或保持信息窗口）按 F3"。
4. 矿物枚举表当时未标完，后由用户提供全表：0=金 1=银 2=铁 3=铝 4=矽 5=煤碳 6=石油 7=化学物 8=木材 9=砂土（与实测吻合）。

### v5 定案：选中对象机制（本阶段最大突破）

- 用户提出"为什么必须进矿场才能改"→ 根因：钩子缓存的是"游戏最后读取的对象"，大地图单击是一次性读取，缓存立刻被刷掉；进入/打开信息窗口后游戏持续读取才能锁住。
- **解法：找到游戏原生选中机制**。对矿场对象挂硬件访问断点（发现该对象平时零访问，只在交互事件时被读写），单击选中瞬间命中，捕获到一个小工具函数（`CEO.exe+5E9C2` 附近，对应 v1.02 语义里的"取选中对象"）：
  ```
  mov edx,[CEO.exe+B1024]   ; 选中对象编号 (dword, -1=无选中)
  mov ecx,[CEO.exe+C43C8]   ; 对象数组步长 (实测 96)
  imul ecx,edx
  add ecx,[CEO.exe+C43DC]   ; 对象数组基址
  mov cl,[ecx+02]           ; 读元素+2 的 FF/00 标志
  ```
  **选中对象地址 = [CEO.exe+C43DC] + [CEO.exe+C43C8] × [CEO.exe+B1024]**，实测单击矽矿场后算出地址与矿场对象完全一致（编号 1336）。
- **对象数组元素布局（最终版，相对元素基址）**：+0 word=ID，+2 byte=FF无建筑/00有建筑，+3 byte=建筑类型(3=矿场)，+4 byte=矿物(0金1银2铁3铝4矽5煤6油7化8木9砂)，+6 byte=品质，+8 dword=储量，+16 word=疑似坐标，+18 dword=FFFFFFFF 无主标记。
- **野矿与空地（用户追问"能不能改野生矿物"后采样实锤）**：矿地与矿场共用同一组字段——野矿地 +2=FF/+3=0/+4=矿种/+6=品质/+8=储量；**空地 +4=255(0xFF)、+8=-1，与矿地可精确区分**。
- ⚠️ **坑 #9：空地"造矿"会闪退**。空地对象的结构变体不同（+4=FF/+8=-1），对它盲写矿物/品质/储量三件套 → 游戏卡死闪退（实测发生一次，游戏重启进程全换）。F3 已收回空地写入，裸地只允许改**已有矿地**（+4 ≠ 0xFF）。空地造矿需先逆向空地→矿地的完整初始化路径（可能涉及数组迁移/渲染层重建），列入待办。
- ⚠️ 野矿改矿种后**未购买地块的贴图不显示变化**——实测确认：**选中矿地时游戏界面会显示该地块数据，购买地块后矿种/品质可见；存档读档后数据保持不回退**（写的是持久化数据）。渲染无变化是游戏对未购买地块本就不显示矿物细节，非修改器问题。
- F3 最终校验：矿场(+2=00,+3=3) 或 已有矿地(+2=FF,+3=0,+4≠0xFF)；其他建筑与空地拒绝写入。
- ✅ **端到端 GUI 实测通过（2026-09-13）**：用户在 CE 加载主表，F2/F3 均工作：矿场 F3 变矿种 ✓；野矿 F3 改矿种 → 购买地块后可见 ✓；存档读档数据持久 ✓。阶段 2 关闭。
- **F3 v5 = 纯 Lua，零代码钩子**：热键读选中编号→算出元素→校验 +3==3（矿场）→按条目值写 +4/+6/+8（-1=不修改）→成功才 beep。大地图单击选中即可改。A36E 钩子已卸载不再需要。
- ⚠️ 选中编号 0 是合法对象，只有 0xFFFFFFFF 表示无选中（第一版 Lua 误把 0 当无选中，已修）。
- **这组全局量（B1024/C43C8/C43DC）是"当前选中对象"的通用入口，阶段 4（F4 强占厂房）、F1（厂房修改）直接复用。**

**② F3 热键 Lua**（表级 `<LuaScript>` 的一部分；`createHotkey` 注册 F3 单键）：

```lua
f3HK = createHotkey(function()
  -- ① 读"选中对象编号"(CEO.exe+B1024), 0xFFFFFFFF=无选中; 注意 0 是合法编号(坑: 不能当无选中)
  local idx = readInteger(iSym)
  if not idx or idx == 0xFFFFFFFF then return end
  -- ② 选中元素地址 = 数组基址(C43DC) + 编号 × 步长(C43C8, 实测96)
  local elem = baseA + stride * idx
  -- ③ 结构校验, 防止把数据写进无关对象:
  --    矿场建筑: +2=00 且 +3=3
  --    已有矿地: +2=FF 且 +3=0 且 +4≠255(+4=255 是空地, 盲写会闪退=坑#9)
  local hdr = readBytes(elem + 2, 3, true)
  local isMine    = hdr[1] == 0x00 and hdr[2] == 3
  local isDeposit = hdr[1] == 0xFF and hdr[3] ~= 0xFF
  if not (isMine or isDeposit) then return end
  -- ④ 三个参数值 >=0 才写对应字段 (-1=不改): 矿物/品质是 byte, 储量是 dword
  --    目标偏移: 矿物=元素+4, 品质=+6, 储量=+8
  if t and t >= 0 then writeBytes(elem + 4, t); written = true end      -- 矿物
  if qv and qv >= 0 then writeBytes(elem + 6, qv); written = true end   -- 品质
  if rv and rv >= 0 then writeInteger(elem + 8, rv); written = true end -- 储量
  -- ⑤ 有实际写入才 beep; 没声音 = 按下时选中的不是可写对象, 重新单击目标即可
  if written then beep() end
end, VK_F3)
```

## 阶段 3：Ctrl+Z/X 快速放置 + Ctrl+V 锁宣传车（实战记录 2026-09-13）

### 定案

- **放置类型全局 = `CEO.exe+4A8C24`**（对应 v1.02 偏移 0x48EFDC）：字节值 **1=主管、2=工人**，0=无。向它写字节后**无需原生拾取**，直接点厂房空槽即放置对应实体。
- **宣传车拾取状态 = `CEO.exe+4D6074`**（对应 v1.02 偏移 0x4BC594，此前会话已静态定位，本次动态验证）：原生拾取宣传车后 = 1。语义与 Z/X 全局独立（拾取宣传车时 Z/X 归 0）。
- 写入值依据 v1.02 反编译：`sub_497085(句柄, 地址, 1或2)`——Z 写 1、X 写 2，与 1.10 原生拾取时观察到的编码一致（拾工人 → 全局=2）。
- 最终实现（主表 Lua，零钩子）：
  - **Ctrl+Z** 切换主管模式 / **Ctrl+X** 切换工人模式（再按取消，beep 反馈）；
  - **Ctrl+V** 锁定宣传车：先原生拾取宣传车，按 Ctrl+V 捕获 4D6074 当前值并持续维持，可反复放置，再按解锁（**原计划 Ctrl+C 与游戏内置 C 键冲突，用户反馈后改 V**）；
  - 100ms `createTimer` 维持写入（v1.02 的 50ms 轮询同款设计，对抗游戏自行重置放置状态）。

### 定位过程与坑

1. **坑 #10：别假设相关全局住在一起**。先对 C 全局周边 4KB 做拾取前后 diff → 零变化（1.10 的 4.4MB 巨型 .data 里两个全局相距很远）。改用**值扫描链**：持主管扫 byte=1（139 万命中）→ 换工人过滤 =2（657）→ 取消拾取 =0（58）→ 再拾主管 =1（9）→ 再换工人 =2（剩 2）→ 唯一静态地址 `CEO.exe+4A8C24`。
2. **行为验证定生死**：写入 1 后"不拾取直接点厂房空槽"放出主管 = 实锤。仅靠扫描命中无法确认（剩两个候选时静态地址只是高嫌疑）。
3. **坑 #11：CE 组合键热键与游戏内置快捷键冲突**。Ctrl+C 是游戏自带的 C 键快捷键组合，按下会双触发；热键选型前先确认游戏快捷键表（改用 Ctrl+V 解决）。
4. 值扫描链全程用 MCP 扫描会话完成（scan_new/scan_next/scan_results），5 轮过滤从 139 万到 2，这是此类"未知状态全局"定位的标准打法。
5. **坑 #12：RVA / VA 两套地址记法混用会得出完全错误的结论**（2026-09-14 核验 1.10 反汇编资源时发现）。本项目同时存在两套体系：CE 里 `CEO.exe+X` 的 X 是 **RVA**（模块内偏移）；IDA / 反汇编资源里的地址是 **VA**，`VA = 0x400000 + RVA`（如金钱 `CEO.exe+D10C0` = VA `0x4D10C0`；放置类型 `CEO.exe+4A8C24` = VA `0x8A8C24`）。
   - **现象**：为验证 `CEO.exe+4A8C24`（放置类型全局）是否被游戏代码引用，在 exe 里搜字节串 `24 8C 4A 00`（把 RVA 当 VA 用）→ **0 命中**，据此判定"该全局无引用、怀疑 Ctrl+Z/X 只是巧合生效"，并写进评估文档当作待核疑点。
   - **正解**：应搜 VA 字节串 `24 8C 8A 00` → **18 命中**；反汇编侧另确认 `sub_4189A0`（拾取人）写 `dword_8A8C24 = 1（主管）/ 2（工人）`，与实测编码完全一致。
   - **铁律**：跨工具检索地址前先换算——查二进制字节用 VA，写 CE 表 / AA 脚本用 `CEO.exe+RVA`；文档中必须标明是哪一套（本记录与主表统一用 RVA）。详见 `厂房自动分配_可行性评估_核验报告.md` §3.2。

### 阶段 3 最终代码全文（主表 `<LuaScript>` 内原文，逐段说明）

```lua
-- 状态变量: gzState=0无/1主管/2工人; cLock=宣传车锁定开关; cLockVal=锁定的原始值
gzHK1 = createHotkey(function()              -- Ctrl+Z: 主管模式开关
  gzState = (gzState == 1) and 0 or 1        -- 再按同组合键 = 取消(归 0)
  beep()
end, VK_CONTROL, VK_Z)                       -- 多键参数 = 组合键(需同时按)

gzHK2 = createHotkey(function()              -- Ctrl+X: 工人模式开关
  gzState = (gzState == 2) and 0 or 2
  beep()
end, VK_CONTROL, VK_X)

gzHK3 = createHotkey(function()              -- Ctrl+V: 宣传车锁 (原 Ctrl+C 与游戏内置冲突)
  if cLock then cLock = false; beep(); return end  -- 已锁定 → 解锁
  -- 开锁前必须先在游戏 UI 原生拾取宣传车, 此刻 4D6074 = 1
  local v = readInteger(getAddress('CEO.exe+4D6074'))
  if v and v > 0 then cLockVal = v; cLock = true; beep() end  -- 捕获当前值用于维持
end, VK_CONTROL, VK_V)

gzTimer = createTimer(nil, false)            -- 100ms 维持定时器 (v1.02 的 50ms 轮询同款)
gzTimer.Interval = 100
gzTimer.OnTimer = function()
  if gzState > 0 then                        -- 模式开启期间持续写放置类型
    writeBytes(getAddress('CEO.exe+4A8C24'), gzState)  -- 1=主管 2=工人
  end
  if cLock then                              -- 锁车期间持续回写拾取状态
    writeInteger(getAddress('CEO.exe+4D6074'), cLockVal)
  end
end
gzTimer.setEnabled(true)
```

（实际代码中每次读写都包 `pcall`，游戏未附加/符号失效时静默跳过；完整原文见主表 `<LuaScript>` 段。）

**为什么需要维持定时器**：游戏会在放置完成/界面交互后自行把放置类型清零，一次性写入只能放一个；定时器每 100ms 重写，保证模式开启期间每次点击都生效——这也是 v1.02 修改器 50ms 轮询的设计意图。

## 厂房任务侦查续（2026-09-14）：表B 岗位结构实锤 + 一次崩溃事故

### 实测确认的结构（全部由活进程读数/游戏内动作验证）

1. **机器面板的四个数字 = 表B 记录的字段**。表B[257]（当前厂房号 143）实测：
   `+0x02`=厂房号、`+0x14`=主管需求、`+0x15`=工人需求、`+0x16`=主管当前、`+0x17`=工人当前；
   `+0x18` 起 20 个 word 主管槽、`+0x40` 起 20 个 word 工人槽（空=0xFFFF）。面板显示 主管 0/0、工人 0/3 与该记录逐字段吻合。
2. **表B 记录 = 每台机器一条"用工岗位"**（不是"厂房本体容器"）：从 `厂房结构+0x2F0` 的链上遍历，本厂（1 台机器）恰好 1 条，其需求值 = 该机器的需求。
   ⇒ 更正此前判断：评估文档 §5.3 推荐调用的 `CEO.exe+185E0`（主管）/`+18730`（工人）**是正确的**——它们写的就是这条机器岗位记录（主管槽 +0x18、工人槽 +0x40）。另一套 `418330`（表A，写 +0x10 槽、人员+0x1C）是地图机器物件的工位，与面板无关。
3. **游戏内"点机器放工人"的动作实锤**：放人前后对比 —— 表B[257] `+0x17` 0→1、工人槽 `+0x40[0]` FFFF→685；人员记录[685] = `类型位0x10(工人)`、`+0x0E`=143(厂房号)、**`+0x1A`=257(表B岗位下标)**、+0x1C/+0x1E=FFFF。表A 本厂记录数始终为 0（未被使用）。
4. **人员记录步长 = 40（0x28）**，非评估文档 §6.3 假设的 0x488（0x488 是别的池的步长）。
5. **编制字段**：厂房 `+0x1D0`=主管编制 5、`+0x1D2`=工人编制 7、`+0x1D4`=在岗主管、`+0x1D6`=在岗工人（实测放 1 人后 →1）。
   ⇒ 更正评估文档 §6.1 假设"编制上限 = 机器需求合计"：实测编制 5/7 而唯一机器只需 0/3，编制是**招聘时逐次累加**的（游戏 UI 配人函数每雇 1 人 `++厂房[+0x1D0/+0x1D2]`）。
6. **全局地址记法更正**：反汇编源码里的 `dword_4CCAAC` 等是 **VA**，CE 里必须写 `CEO.exe+CCAAC`（= VA − 0x400000）。评估文档 §4.2 的全局表把 VA 直接写成了 `CEO.exe+X` 形式，照抄到 CE 会全部读错（本次已踩）。

### ⚠️ 坑 #13：直接调用游戏函数前必须核对调用约定，否则崩游戏

**现象**：为取机器岗位坐标，用 `executeCodeEx(0, ...)` 以 cdecl 方式调用 `sub_426BF0(记录, &x, &y)`；调用"成功返回"，但随后游戏进程消失（崩溃）。
**根因**：`sub_426BF0` 的真身是 **`__thiscall`**（`this` 走 ECX），
```c
int __thiscall sub_426BF0(__int16 *this, int a2, int a3)
```
按 cdecl 调用时 ECX 是垃圾值 → 函数把它当结构指针解引用（`*(this+1)`/`*(this+8)`）→ 访问非法内存；同时栈参数错位，把输出坐标写进了 `记录` 指向的地址（污染表B 记录头 8 字节）。
**解法/铁律**：
1. 调用任何游戏函数前，**先读伪代码确认调用约定**（`__cdecl` / `__thiscall` / `__stdcall` / `__fastcall`）与参数顺序；
2. `__thiscall` 用 `ce_execute_method`（`class_instance` = this 指针，`instance_register=1` 即 ECX）或 `ce_call_function(call_method=4)`，**不要**用 cdecl 平铺参数；
3. 优先选**只读**途径拿数据（例：取机器格子坐标可直接查 `厂房[+0x8C]` 格表里值为物件下标的那一格），能不求值就不调函数；
4. 调用类实验前告知用户"可能崩游戏"，并确认游戏进度已存档。
**损失**：游戏进程崩溃，需重启并重载存档；本次未触碰存档文件（纯内存操作），文档与代码产物无影响。

### ⚠️ 坑 #14：无参、cdecl 的游戏函数也可能崩 —— 缺"运行时上下文"同样致命

**现象**：调用 `sub_45A8D0`（游戏自带的"把当前厂房各岗位按需求配满"函数，**无参数**、编译为默认调用约定）→ 返回 1（看起来成功）→ 但游戏进程随即死亡。这是本次任务第二次崩游戏（第一次见坑 #13）。
**根因（待验证，当前为主假设）**：游戏函数依赖**运行时上下文**，在正常流程之外调用会踩到未初始化的全局。最可疑的是生成人链路：
```
45A8D0 → 4185E0/418730 → 42BD50 →
    sub_4656D0(&dword_4D1090)                    // 人员临时池
    *(char *)(*(_DWORD *)dword_4D10B0 + 3/11/..) // 携带描述符数组（由"拾取实体"流程初始化）
```
若玩家从未拾取过实体，`dword_4D10B0` 可能仍为 0 → 解引用空指针 → 崩。
**诊断方法（只读，安全）**：游戏内正常游玩状态下读 `CEO.exe+D10B0`；再在游戏里"拾取一个实体"后复读，看是否从 0 变为有效指针。
**铁律（升级版）**：
1. **调用约定正确只是必要条件，不是充分条件**——还要确认函数依赖的全局/上下文已就绪；
2. 类调用实验前必须：① 用户存档；② 明确告知"可能崩游戏"；③ 一次只调一个函数并立即验证；
3. 连续两次崩溃说明该路线风险不可控 → **改用"用户做一次原生动作建立上下文"或"数据直写复用已有对象"或"模拟点击走完整原生流程"**（v1.02 修改器选的就是最后一条，用 mouse_event）；
4. 任何时候能用只读方式拿到数据，就不要调函数。

### 作弊控制台的自动化调用（已实现进主表，2026-09-14）

**目标**：把"按 Ctrl+F5 + 手输命令"变成热键一键完成。

**技术方案（三段，全部实测通过）**：

```lua
-- ① 打开控制台: 左Ctrl 用 keybd_event 设"真实键状态"(骗过游戏的 GetAsyncKeyState 判定),
--    F5 用 SendMessage 发 WM_KEYDOWN/UP 给游戏窗口
executeCodeEx(0, nil, getAddress('keybd_event'), 0xA2, 0x1D, 0, 0)   -- 左Ctrl 按下
SendMessage(hwnd, 0x100, 0x74, 0x003F0001)                            -- WM_KEYDOWN F5
SendMessage(hwnd, 0x101, 0x74, 0xC03F0001)                            -- WM_KEYUP   F5
executeCodeEx(0, nil, getAddress('keybd_event'), 0xA2, 0x1D, 2, 0)   -- 左Ctrl 抬起
-- ② 输入命令: WM_CHAR 逐字 (50ms 间隔)
SendMessage(hwnd, 0x102, string.byte(ch), 1)
-- ③ 执行: SendMessage 发回车 (控制台会自动关闭并执行命令)
SendMessage(hwnd, 0x100, 0x0D, 0x001C0001)
SendMessage(hwnd, 0x101, 0x0D, 0xC01C0001)
```

**验证方式（关键技巧）**：读游戏内部的"控制台已创建"标志 `CEO.exe+4CAF74`（命令处理器创建控件时 `mov dword [0x8caf74],1`），可确认打开成功；执行后该标志归 0 = 命令已受理。

**踩过的细节**：
1. `keybd_event` 在 CE Lua 里**不是全局函数**，但 `getAddress('keybd_event')` 能解析 → 用 `executeCodeEx` 调用即可；
2. **字符输入用 `keybd_event` 会漏字**（按键保持 30ms 太短，游戏漏掉），改用 **WM_CHAR** 稳（也更快）；
3. **回车必须用 `SendMessage`**：用 keybd_event 发回车没被控制台接受（且一旦游戏失去前台焦点就完全无效）；SendMessage 版本**不要求游戏在前台**，实测在后台也能执行；
4. 输入前先检查控制台标志，未打开就不输入，避免把命令文字误打进游戏；
5. 热键选型：查游戏按键分发表后确认 **F6~F12 未被游戏占用**（游戏占用 Enter/Esc/B/C/D/F/M/P/Q/R/S/F5/小键盘±/`=`/`-`）。
