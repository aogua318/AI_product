> 决策结论：**放弃继续"逐点移植 v1.02 修改器"，改用"以 v1.02 逻辑为规格、CE 实时调试、面向 v1.10 重新开发"** 的路线。本文档为该决策与开发计划的存档。

## 1. 决策背景与理由

### 1.1 移植路线的实证结果（为什么转向）

对 Steam 版 1.10（`D:\gameapp\Steam\steamapps\common\創業王\CEO.exe`，816KB）的分析确认：

- 1.10 是**重新编译链接**的版本：代码 640KB 与 v1.02 相当，但布局完全重排（v1.02 的 ".text+尾部BSS" 结构 → ".text + .data 巨型 BSS"，节区 3→5，非加壳）；
- v1.02 修改器的 10 个 AA 脚本钩子点中，**9 个的原始指令序列在 1.10 中已不存在**（字节级匹配证伪）——1.10 恰好重写了金钱结算、归属扫描、生产推进、建设队列、年代过滤这些被钩的玩法代码；
- 结论：移植 = 在 1.10 里把每个钩点**按语义重新找一遍**，工作量与重新开发几乎相同，却还背着旧壳和旧架构的包袱。

### 1.2 重新开发路线的优势

1. **规格现成**：v1.02 修改器已被完整逆向——10 段 AA 脚本（每段 = 一条作弊规则的语义答案：钩哪个逻辑、改什么、怎么判）、Ctrl+Z/X/C 的读改写逻辑、数据结构（放置类型全局、厂房对象指针槽、GameState）。
2. **调试工具即开发工具**：CE 本身就是内存扫描 + "什么改写/访问" + AA 注入 + 热键的一体化环境，找点位和写功能在同一个工具里闭环，所见即所得。
3. **产物可维护**：产出是一张 .CT 表（点位仓库），1.11/1.11b 出来只需在表里更新特征串；也可以随后打包成独立修改器。
4. **已验证的起点**：F3 钩点（0x40A36E）与 Ctrl+C 全局（0x8D6074）已用指令级证据在 1.10 定位完成，等于两条功能线已经开工。

## 2. 功能开发计划（逐项：v1.02 参照逻辑 → 1.10 定位方法 → 验收标准）

### 阶段 0：环境准备（约 30 分钟）

- [ ] 安装 Cheat Engine 7.x（官网下载，本机当前未装）
- [ ] 启动 1.10 游戏（Steam 目录 CEO.exe，无 steam_api 依赖，预期可脱网直启——需实测一次）
- [ ] CE 附加游戏进程，确认可扫描内存（游戏为老 DirectDraw 单机，无反作弊）
- [ ] 建立工作目录 `CT表\` 与开发记录

### 阶段 1：F2 金钱无限（最标准流程，约 30-60 分钟）✅ 已完成（2026-09-13）

- v1.02 参照逻辑（脚本 s00）：钩金钱结算点（0x4202E3），当 `[reg+738]` 标志成立时跳过 `sub ecx,eax`（扣钱），保持金额不变
- 1.10 步骤：
  1. 游戏内记下当前金钱 → CE 首次扫描
  2. 消耗/获得金钱 → 再次扫描 → 锁定金钱地址
  3. 右键"找出是什么改写了这个地址" → 得到扣钱指令及其所在函数
  4. 对照 v1.02 脚本语义（跳过扣款）写 AA 注入脚本：`cmp [标志],0 / jne 原逻辑 / 跳过扣款`
  5. 绑定 F2 热键
- 验收：开关 F2，付款时金钱不减；关闭后恢复正常扣款
- 备注：若 1.10 金钱结构改为 float/long，扫描类型相应调整；`[reg+738]` 标志在 1.10 是否仍存在需实测（v1.02 中为游戏自带状态位）

**1.10 实测定案（最终脚本 = `v1.10CE数据\CEO_v1.10_F2.ct`）**：

- 金钱 = **Double** @ `CEO.exe+D10C0`，记录结构基址 = `CEO.exe+D10B8`（esi 指向记录，[esi+8] 为金额）
- 钩点 = **`CEO.exe+2EE0D`**（对应 v1.02 s00 @0x4202E3 的结算函数）：原始 12 字节 `fld[ebp+08] / movsx / fadd[esi+08] / fstp[esi+08]`，返回点 2EE19（`cmp eax,[x]` 疑似交易类型分支，备用）
- 作弊语义：金额（double，**支出为负数**）符号判断（ftst/sahf/jae），负数且开启时原额写回；收入（≥0）放行。对应 v1.02 s00"只跳扣款"
- 支出经此路径写入已用硬件断点实锤（命中 RIP 在钩子内 fstp）
- **关键教训 1：CEO.exe 每次启动被重定位（本次基址 0x2F0000，非默认 0x400000）——所有脚本一律用 `CEO.exe+偏移` 符号，禁止硬编码绝对 VA**（第一版脚本 `cmp esi,4D10B8` 因重定位永不匹配，钱照扣）
- **关键教训 2：CE AA 不支持 `4D10B8h` 的 h 后缀十六进制**（静默导致勾选失败）；CT 的 XML 里脚本注释不能出现裸 `<`
- 实测：开启后买地支出金额不减（30,000,000 → 花费后 20,368,500 两次不变）；收入路径待观察一次发工资确认

### 阶段 2：F3 矿物/品质/储量修改（✅ 完成并实测 2026-09-13，详见实战记录阶段 2 章节）

- 钩子 0x409E1B → **0x40A36E**（已验证）；数据槽 0x4A7848 → 0x4F7048
- ⚠️ 注意：以上均为"假设基址 0x400000"的 VA。实测 CEO.exe 会被重定位（如 0x2F0000），迁移进表时一律换算成 `CEO.exe+偏移` 形式（0x40A36E → CEO.exe+A36E，0x4F7048 → CEO.exe+F7048），并实测校验
- 实测定案（v5 最终版）：**F3 = 纯 Lua + 游戏原生选中机制，零代码钩子**。选中对象地址 = [CEO.exe+C43DC] + [CEO.exe+C43C8]×[CEO.exe+B1024]（编号/步长/基址三全局，硬件断点实锤），大地图单击选中即可改；对象元素布局：+3=建筑类型(3=矿场)、+4=矿物(0金1银2铁3铝4矽5煤6油7化8木9砂)、+6=品质、+8 dword=储量，三项均写值实测生效；野矿同样可改（购买地块后可见，存档持久）；品质/储量为超出 v1.02 的新增功能；v1.02 的 s01 钩子（A36E）已验证后被取代卸载；空地造矿盲写会闪退已禁用（待研究）。选中机制三全局将复用于阶段 4/F1
- 动作：把已有 AA 脚本的符号替换后录入 .CT 表，绑定 F3
- 验收：点击地图任意地块按 F3，矿物类型按 UI 选择改变

### 阶段 3：Ctrl+Z/X 快速放置 + Ctrl+V 锁宣传车（✅ 完成并实测 2026-09-13，详见实战记录阶段 3 章节）

- v1.02 参照逻辑：读改写"放置对象类型"全局（v1.02: 0x48EFDC / 0x4BC594），播放音效，50ms 轮询维持
- 1.10 实测定案：**纯 Lua 实现，零钩子**。放置类型全局 = `CEO.exe+4A8C24`（1=主管 2=工人，写后无需原生拾取直接点空槽放置）；宣传车状态 = `CEO.exe+4D6074`（原生拾取后=1，Ctrl+V 捕获并维持=锁，可反复放置）；100ms Lua 定时器维持写入；再次按压同组合键取消
- 坑：Ctrl+C 与游戏内置快捷键冲突 → 改 Ctrl+V；Z/X 全局定位用值扫描链（139万→657→58→9→2）+ 不拾取直接放置的行为验证

### 阶段 4：F4 强占厂房 + Alt+1/2/3 快速购地（约 1-2 小时）

- v1.02 参照逻辑（脚本 s04-s06）：钩 0x42025F/68/6E，改写归属字段写入路径（对象 +0x1Ch 为归属 word，FFFF=无主）
- 1.10 步骤：点击一块地 → CE "找出是什么访问" → 定位归属扫描/写入函数 → 按 v1.02 语义改写
- 验收：Alt+1/2/3 后地块归属立即变为玩家

### 阶段 5：F5 秒建设 + 机器秒生产（约 1-2 小时）

- v1.02 参照逻辑（脚本 s07-s09）：钩 0x4204FC（建设队列）与 0x42790F/27765（`mov [eax],C3500`=写 800000、生产计数 +1）
- 1.10 步骤：
  1. 机器秒生产：找生产进度/计时字段（点击机器 → "什么访问"），或直接搜常量 800000 的写入点
  2. 秒建设：找建设进度字段
  3. 按 v1.02 语义（计数 +1 / 直接写完成值）做 AA 注入
- 验收：建设中厂房与机器立刻完工；生产第一次正常、后续无限（与说明.txt 行为一致）

### 阶段 6：打包与收尾（约 1 小时）

- [ ] 全功能在 .CT 表中验证通过
- [ ] 可选：CE Trainer Generator 打包为独立 exe；或复用 `loader_v110.py` 骨架写成自有启动器

| 风险 | 影响 | 对策 |

## 5. 设计约束（写给未来的实现者）

1. 新修改器一律采用 **AOB 特征码自定位**（v1.02 修改器吃过的亏：纯静态偏移跨版本必死）；
2. 不绕过游戏自身的合法性判断（防崩溃，见 §3）；
3. 每个功能在 .CT 表/代码中注明 v1.02 原始语义出处（脚本编号），便于后续版本再对照；
4. 游戏本体文件永远只读——所有修改走运行时内存（延续本项目一贯原则）。
