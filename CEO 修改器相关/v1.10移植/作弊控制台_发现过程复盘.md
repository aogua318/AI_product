## 0. 一句话概括

**在连续两次"直接调用游戏函数导致游戏崩溃"之后，我放弃继续试函数，转而反查"这个函数到底是被谁调用的"——结果发现调用者是一个命令分发器（一串 `strcmp`），顺着它又找到触发它的按键，从而发现了游戏自带的作弊控制台。**

核心方法：**调用图反查 + "无代码调用者"这个信号 + 跳转表解码**。

## 1. 缘起：一个"新需求"如何把路引到控制台

### 1.1 任务起点

用户提出：「能不能做到给当前厂房里的所有机器自动分配工人与主管」。
我评估后决定走"路线 1：数据直写"，先侦查数据结构，再决定实现方式。**当时完全不知道游戏自带这个功能。**

### 1.2 侦查第一步：确认"当前厂房"可以定位

借用此前 F3 功能摸清的**选中对象机制**三全局：

```
选中元素 = [CEO.exe+C43DC] + [CEO.exe+C43C8] × [CEO.exe+B1024]
                                        ↑ 步长=96      ↑ 编号
```

进入厂房视图后读取该元素，得到 `+4`=矿种、`+6`=品质、`+8`=储量，与厂房侧栏显示一致 → 确认"选中对象 = 当前厂房的地图对象"。

### 1.3 侦查第二步：读厂房结构时踩了 RVA/VA 的坑（第一次自我纠错）

我按反汇编源码里的变量名去读 `CEO.exe+4CCAAC`（厂房数组基址）等，结果**全部读到 0**。原因是：

- 反汇编源码里的 `dword_4CCAAC` 是 **VA**（虚拟地址）；
- CE 里 `CEO.exe+X` 的 X 是 **RVA**（模块内偏移）；
- 换算：`VA = 0x400000 + RVA` → 正确写法是 `CEO.exe+CCAAC`。

改成正确地址后立刻读到了真实数据：

```
厂房结构=0x1D855110: 主管编制(+0x1D0)=5  工人编制(+0x1D2)=7
                     在岗主管(+0x1D4)=0  在岗工人(+0x1D6)=0
表B链头(+0x2F0)=257
```

（这个坑后来编号为**坑 #12**，并升格为项目铁律：跨工具检索地址必须先换算、文档必须标注是哪一套。）

### 1.4 侦查第三步：确认"表B = 每台机器一条用工岗位"

沿 `厂房+0x2F0` 的链读到 `表B[257]`，其字段与用户报的机器面板数字**逐字段吻合**：

```
表B[257]: +0x14=0  +0x15=3   ← 需求：主管 0 / 工人 3
          +0x16=0  +0x17=0   ← 当前：主管 0 / 工人 0
          +0x18 起 20 个 word 主管槽；+0x40 起 20 个 word 工人槽（空=FFFF）
```

厂房里只有 1 台机器，链上就只有 1 条记录，且需求值正好是该机器的需求 → **表B 记录是"每台机器一条用工岗位"**。

### 1.5 侦查第四步：让用户做一次原生动作，用内存前后对比实锤

请用户在游戏里原生拾取一个工人、点到机器上，前后对比：

```
表B[257]: 当前工人 +0x17  0 → 1
          工人槽 +0x40[0]  FFFF → 685
人员记录[685]: 类型位=工人, 厂房号=143, +0x1A=257(该岗位下标), +0x1C/0x1E=FFFF
厂房 在岗工人 +0x1D6: 0 → 1
```

**闭环成立**：工人被分配到机器上 = 写表B 岗位记录的槽位与计数 + 人员记录回指岗位下标。

### 1.6 侦查第五步：想要坐标，结果崩了游戏（第一次崩溃）

放人函数需要**格子坐标** `(x, y)`。我从反汇编里找到游戏自己取坐标的函数 `sub_426BF0`（`sub_45A8D0` 与 AI 配人逻辑都用它取岗位坐标），于是用 CE 调用：

```lua
executeCodeEx(0, nil, getAddress('CEO.exe+26BF0'), 记录指针, 输出X, 输出Y)  -- 按 cdecl 传参
```

调用"成功返回"，但读到的坐标是 0；紧接着下一个 CE 调用发现**游戏进程已经消失**。

**根因（事后读伪代码确认）**：

```c
int __thiscall sub_426BF0(__int16 *this, int a2, int a3)   // ← thiscall! this 走 ECX
```

我按 **cdecl** 调用 → ECX 里是垃圾值，函数把它当成结构指针解引用（`*(this+1)`、`*(this+8)`）；同时栈参数错位，把输出坐标写进了记录指针指向的地址（污染了表B 记录头 8 字节）。**这是我自己的调用约定错误，必崩。**（坑 #13）

### 1.7 侦查第六步：换个思路，结果又崩了（第二次崩溃 → 真正的转折）

重启游戏、用户放了一台重型加工机（面板 `0/1 0/2`）后，我读了新的岗位记录：

```
表B[287]: 需求 主管1/工人2  当前 0/0  物件下标=2
物件[2]:  类别(+0x0B)=0  关联(+0x0C)=287      ← 与岗位互相指向
机器占格: (4,3)(5,3)(4,4)(5,4)(4,5)(5,5)(4,6)(5,6)
```

同时发现**厂房编制是 0/0**（用户还没雇人）。而放人函数开头都有这道检查：

```c
if ( 厂房[+0x1D0] - 厂房[+0x1D4] <= 0 ) return 0;   // 编制余量为 0 → 直接失败
```

也就是说：编制不够时，直接调放人函数**永远返回失败**。

这时我想到：**游戏自己一定有一键配人的逻辑**——因为我在之前核验《厂房自动分配_可行性评估》这份文档时，读过 `sub_45A8D0` 的伪代码：它遍历厂房岗位链、按需求补人、每雇一人自动把编制 +1 并扣招聘费。当时我把它理解为"游戏 UI 的配人按钮"。它**无参数、cdecl**，看起来可以安全调用：

```lua
ce_call_function(address='CEO.exe+5A8D0', args=[], call_method=0)
-- 返回 1（看起来成功）
```

**但游戏进程随即再次死亡。**（坑 #14）

### 1.8 第二次崩溃后的只读诊断：我的假设被推翻

我原本假设"生成人链路依赖一张由'拾取实体'初始化的全局表，没拾取过就是 0 → 空指针"。于是重启游戏、载入存档，**只读**核查：

```
dword_4D10B0 (携带描述符数组指针) = 0x158C95B0   ← 非 0！假设被推翻
dword_4CD128 (生成变体比较值)     = 0
dword_4D1090 (人员临时池)         = 0x2
```

再把描述符表逐条解析（8 字节/条：`+0` 物件ID、`+2` 类型、`+3` 阈值）：

```
条目0: 物件ID=21 类型=1(主管) 阈值=0   → 比较成立
条目3: 物件ID=33 类型=0(工人) 阈值=0   → 比较成立
```

**表结构完全正常，v16（生成变体索引）能被正确赋值 0 或 3** → 崩溃不是"描述符未初始化"。

**此时我做出了本次任务最关键的一个决定：**

> 两次崩溃都出在"从外部直接调用游戏函数"这条路上，而我对原因的猜测已被推翻。
> **不再继续盲试函数**，转而调查一个从没问过的问题：**`sub_45A8D0` 到底是被谁调用的？**

## 2. 转折点：反查调用者，发现命令分发器

### 2.1 用调用图查 `45A8D0` 的调用者

反汇编资源包里带了全量调用图 `03_分析数据/callgraph.json`（格式：函数 → 它调用的函数列表）。我写了个小脚本反查"谁调用了它"：

```python
import json
cg = json.load(open('03_分析数据/callgraph.json', encoding='utf-8'))
target = '0x45a8d0'
callers = [k for k,v in cg.items() if isinstance(v,list) and any(str(x).lower()==target for x in v)]
# → ['0x45a9d0']
```

**得到 `0x45A9D0`。** 读它的伪代码：

```c
void __cdecl sub_45A9D0(int a1, int a2)
{
  if ( !a2 ) {
    // 把 dword_8CB0A0+28 处的字符串复制到 v6 (256 字节缓冲)
    ...
    if      ( !strcmp(v6, "money") )       { /* 所有公司 +1 亿 */ }
    else if ( !strcmp(v6, "money1") )      { /* 本公司 +1 亿 */ }
    else if ( !strcmp(v6, "wkrfill") )     { sub_45A8D0(); }        // ← 我要的功能！
    else if ( !strcmp(v6, "notalk") )      { dword_8CAF70 = 1; }
    else if ( !strcmp(v6, "talk") )        { dword_8CAF70 = 0; }
    else if ( !strcmp(v6, "buildok") )     { sub_45A730(dword_4B1024); }
    else if ( !strcmp(v6, "buildokall") )  { sub_45A8B0(); }
    sub_45AC20(0);      // 收尾：销毁输入控件
  }
}
```

**这就是作弊控制台的命令处理器。** 原来 `wkrfill` 就是"一键配满厂房人力"，是控制台命令之一。

### 2.2 关键旁证：它**没有**任何代码调用者

查 `45A9D0` 的调用者：

```python
callers = [k for k,v in cg.items() if isinstance(v,list) and any(str(x).lower()=='0x45a9d0' for x in v)]
# → []      （空！）
```

一个函数被调用图完全找不到调用者，只有两种可能：① 通过函数指针/虚表调用；② **由界面资源表驱动**（本游戏是数据驱动界面：`.fce` 界面文件里引用处理函数）。
考虑到它位于 `Business_UI` 模块、且参数 `(a1, a2)` 像是"控件事件 + 通知码"，我判断是**②资源驱动**。

## 3. 静态定位六步：从"有个处理器"到"按 Ctrl+F5"

### 步骤 1：在 exe 里搜它的 VA 字节序，找到引用点

资源表里引用函数会用**绝对 VA**（该 exe 基址 0x400000，加载时由 .reloc 重定位）。`45A9D0` 的 VA 是 `0x0045A9D0`，小端字节序为 `D0 A9 45 00`：

```python
d = open('CEO.exe','rb').read()
d.find(bytes.fromhex('D0A94500'))   # → 文件偏移 0x5A079
```

**唯一命中一处。** 换算成 RVA：`0x5A079 - 0x400 + 0x1000 = 0x5AC79`（.text 节 RVA 0x1000 ↔ 文件偏移 0x400）。

> ⚠️ 这个"把 VA 字节序拿去搜"的动作，正是 §1.3 里踩过的同一个坑的正向应用——**字节检索用 VA，CE 用 RVA**。

### 步骤 2：反汇编引用点，看到"创建输入控件 + 注册回调"

反汇编 RVA `0x5AC20` 起（`sub_45AC20`）：

```asm
RVA 0x05AC20  push ebp / mov ebp,esp
RVA 0x05AC23  cmp dword ptr [ebp+8], 0
RVA 0x05AC27  je 0x45ac98                     ; 参数为 0 → 走销毁分支
RVA 0x05AC29  cmp dword ptr [0x8caf74], 0
RVA 0x05AC30  jne 0x45acc4                    ; 已创建过 → 跳过（幂等）
RVA 0x05AC36  push 1
RVA 0x05AC38  push 0x4a4500                   ; ← 字符串 VA
RVA 0x05AC3D  call 0x47c740
RVA 0x05AC46  mov ecx, 0x8caf78 / call 0x481c90   ; 构造控件对象
RVA 0x05AC50  push 0x122 / push 0x8c / call 0x482f10   ; 设置尺寸 290×140
RVA 0x05AC78  push 0x45a9d0                   ; ★ 回调 = 命令处理器
RVA 0x05AC7D  push 0x8caf78
RVA 0x05AC82  mov ecx, 0x4c3108 / call 0x47d1a0   ; 注册回调
RVA 0x05AC8C  mov dword ptr [0x8caf74], 1     ; ★ 置"已创建"标志 = CEO.exe+4CAF74
```

于是得到三个关键坐标：
- **控制台标志** `CEO.exe+4CAF74`（=VA 0x8CAF74）——可用于判定"控制台是否已打开"；
- **输入控件对象** `0x8CAF78`；
- **文本缓冲对象指针** `dword_8CB0A0`（见 §2.1 处理器里读 `+28` 处的字符串）。

### 步骤 3：读那个字符串，看到 `face\face_cheat.fce`

`0x4A4500` 是 VA → RVA `0xA4500` → .rdata（RVA 0xA2000 起，文件偏移 = RVA − 0x1A00）→ 文件偏移 `0xA2B00`。读出来是：

```
face\face_cheat.fce      ← 作弊界面！
face\face_mapedit.fce
face\extface_putland.fce
face\ceo_regist.fce
```

而紧挨着它前面的一段字符串池（文件偏移 0xA2A90~0xA2B60）里，赫然是那批命令：

```
buildokall / buildok / talk / notalk / wkrfill / money1 / money
```

**字符串布局本身佐证了"命令 → 作弊界面"是一套东西。**

### 步骤 4：找"谁创建控制台"，从而找到触发键

`sub_45AC20` 有 3 处调用点。既然资源表里搜不到，就**扫全 .text 的 `E8`（call）指令反算目标**：

```python
for i in range(TEXT_RAW, 0xA0600):
    if d[i] != 0xE8: continue
    rel = struct.unpack_from('<i', d, i+1)[0]
    rva = i - TEXT_RAW + TEXT_RVA
    if 0x400000 + rva + 5 + rel == 0x45AC20:
        hits.append(hex(rva))
# → ['0x96a6', '0xaf12', '0x5ac05']
```

反汇编 `RVA 0x9690`（按键处理函数内的调用点）：

```asm
RVA 0x009690  push 0xa2
RVA 0x009695  call dword ptr [0x4a21c0]     ; GetAsyncKeyState(0xA2)
RVA 0x00969B  test ax, ax
RVA 0x00969E  jns 0x409f4e                  ; 高位未置位（键没按下）→ 跳过
RVA 0x0096A4  push 1
RVA 0x0096A6  call 0x45ac20                 ; ★ 创建控制台
```

**`0xA2 = VK_LCONTROL`（左 Ctrl）** —— 这就是条件。
再看另一处 `RVA 0xAF03`：

```asm
RVA 0x00AF03  push 0x1b
RVA 0x00AF05  call dword ptr [0x4a21c0]     ; GetAsyncKeyState(0x1B)
RVA 0x00AF0E  jns 0x40af1a
RVA 0x00AF10  push 0
RVA 0x00AF12  call 0x45ac20                 ; ★ 参数 0 = 销毁控制台
```

**`0x1B = VK_ESCAPE` → ESC 关闭控制台。**

### 步骤 5：解码按键分发表，确定是"哪个键 + Ctrl"

上面那段代码位于一个**键盘消息处理器**（RVA `0x95E0` 起）的某个 case 里。它的分发结构是：

```asm
RVA 0x0095FF  mov eax, [ebp+8]              ; 键码（WM_KEYDOWN 的 wParam）
RVA 0x009602  add eax, -0xd                 ; 减 13
RVA 0x009605  cmp eax, 0xb0
RVA 0x00960A  ja 0x409f50                   ; 超出范围 → 默认分支
RVA 0x009610  movzx eax, byte ptr [eax + 0x409f9c]   ; ① byte 表 (VA 0x409F9C)
RVA 0x009619  jmp dword ptr [eax*4 + 0x409f60]        ; ② dword 跳转表 (VA 0x409F60)
```

即：**键码 → `(键码-13)` 查 byte 表得 case 索引 → 查 dword 跳转表得目标地址**。

我写脚本把两张表都读出来（VA→文件偏移换算：.text 的 `off = VA - 0x400000 - 0x1000 + 0x400`）：

```python
bt = [d[fo(0x409F9C)+i] for i in range(177)]        # byte 表 177 项
jt = [struct.unpack_from('<I', d, fo(0x409F60)+i*4)[0] for i in range(20)]
# jt[13] = 0x409690   ← 正是"创建控制台"那段代码！
idx = [i for i,x in enumerate(jt) if x == 0x409690]  # → [13]
codes = [c for c in range(13,190) if bt[c-13] == 13] # → [116]
```

**`116 = 0xF5 = VK_F5`。**

于是完整触发条件确定：**按住左 Ctrl 再按 F5**。
（顺带把整张表都解出来，得知游戏占用了 Enter/Esc/B/C/D/F/M/P/Q/R/S/F5/小键盘±/`=`/`-` —— 这为后面选热键避免冲突提供了依据。）

### 步骤 6：确认"命令只有这几条"（穷尽性验证）

因为要做成热键，必须知道命令全集。做了五重验证（详见 `v1.10修改器_成果总览与后续路线.md` §2.2）：

1. 全量反编译源码提取所有 `strcmp` 字面量 → 命令型仅 7 个（外加 `go`，属对话框逻辑）；
2. 命令所在界面 `face_cheat.fce` 仅 91 字节，`face_cheat.h` 枚举**只有 `EDIT_CHEAT` 一个控件** → 没有别的按钮；
3. 文本缓冲对象 `dword_8CB0A0` **全游戏仅被 `45A9D0` 引用** → 不存在第二处文本命令入口；
4. 地图编辑器界面 `face_mapedit.fce` 只有 `BTN_EXIT/LIST1/UNUSE_OBJ3`，无文本输入；
5. 游戏那些单键（B/C/D/F/M/P/Q/R/S）反汇编抽查 → 都是正常玩法快捷键，非作弊。

## 5. 从"能用"到"好用"：自动化调用的技术细节

目标：把"Ctrl+F5 + 手输命令"变成热键一键完成。**原则：不再调用任何游戏函数**（两次崩溃的教训），改走用户级输入路径。

### 5.1 三段式方案（全部实测通过）

```lua
-- ① 打开控制台：左Ctrl 用 keybd_event 设"真实键状态"（骗过游戏的 GetAsyncKeyState 判定）
executeCodeEx(0, nil, getAddress('keybd_event'), 0xA2, 0x1D, 0, 0)   -- 左Ctrl 按下
SendMessage(hwnd, 0x100, 0x74, 0x003F0001)                            -- WM_KEYDOWN F5
SendMessage(hwnd, 0x101, 0x74, 0xC03F0001)                            -- WM_KEYUP   F5
executeCodeEx(0, nil, getAddress('keybd_event'), 0xA2, 0x1D, 2, 0)   -- 左Ctrl 抬起
-- ② 逐字输入命令（WM_CHAR，间隔 50ms）
SendMessage(hwnd, 0x102, string.byte(ch), 1)
-- ③ 回车执行（控制台自动关闭）
SendMessage(hwnd, 0x100, 0x0D, 0x001C0001)
SendMessage(hwnd, 0x101, 0x0D, 0xC01C0001)
```

执行前先读 `CEO.exe+4CAF74`（§步骤2 发现的"已创建"标志）确认控制台真的开了，**没开就不输入**，避免把命令文字误打进游戏。

### 5.2 这条路线上踩的四个细节

1. **CE Lua 里没有 `keybd_event` 全局函数**，但 `getAddress('keybd_event')` 能解析出地址 → 用 `executeCodeEx` 调用即可（`mouse_event` / `getForegroundWindow` / `findWindow` / `SendMessage` 则是现成的）；
2. **必须先让游戏在前台**：一开始游戏不在前台，注入的按键全跑到别处去了，控制台标志一直是 0 → 用 `SetForegroundWindow` 主动切前台（**后来发现只有 Ctrl 需要真实键状态，F5/文字/回车改走 SendMessage 后就不再需要前台了**）；
3. **字符输入用 `keybd_event` 会漏字**：按键只保持 30ms 时游戏漏掉字符。我先读控制台**输入缓冲**（`[CEO.exe+4CB0A0]+0x28`）确认字符有没有到达，加长按住并补上扫描码后成功；最终改用 `WM_CHAR` 更稳更快；
4. **回车必须用 `SendMessage`**：用 `keybd_event` 发回车不被控制台接受（且游戏一失去前台就彻底无效）。改用 `SendMessage` 发 `WM_KEYDOWN/WM_KEYUP(VK_RETURN)` 后一次成功——用无害命令 `notalk`/`talk` 做的验证（读对话标志 `CEO.exe+4CAF70` 判定生效：0→1→0）。

### 5.3 最终落地

主表 `CEO_v1.10_主表.ct` 绑定热键（**不要求游戏在前台**，每次成功"哔"一声）：

| 热键 | 命令 | 作用 |
|---|---|---|
| F6 | `wkrfill` | 一键配满当前厂房各岗位人力 |
| F7 | `buildok` | 当前选中物件一键完工 |
| F8 | `buildokall` | 全部建造完工 |
| F9 | `money1` | 本公司 +1 亿 |
| F10 | （仅打开） | 手动输入其他命令 |

## 6. 方法提炼（可复用的 7 条）

1. **崩溃之后不要重复盲试**。两次直接调函数崩溃、且我的成因假设被只读诊断推翻后，正确的动作是**换问题**：不问"怎么把它调起来"，改问"游戏自己是怎么把它调起来的"。
2. **调用图反查是最省力的一招**。`callgraph.json` 反查调用者，一步就从"一个用途不明的配人函数"跳到了"命令分发器"，也就是功能的真正入口。
3. **"没有任何代码调用者"是一个强信号，不是死路**。它通常意味着"由资源/数据表驱动"——方向应转向 exe 的**数据段与资源文件**（本游戏就是 `.fce` 界面资源）。
4. **VA/RVA 必须分清**：字节检索用 VA（`VA = 0x400000 + RVA`），CE 用 RVA。同一个坑我在同一天里踩了一次（读全局读到 0）、又正向用了一次（搜函数引用一击命中）。
5. **跳转表解码**是定位"哪个键/哪个消息"的标准手法：读 byte 表 + dword 表，再反查键码。同理可用于任何"消息分发"场景。
6. **字符串池的邻接关系是有力旁证**：命令字符串紧挨着 `face_cheat.fce` 字符串，二者同属一套功能。
7. **验证要借用游戏自己的状态标志**：控制台标志 `4CAF74`、对话标志 `4CAF70`、输入缓冲 `[4CB0A0]+0x28`——用它们可以程序化判定"打开/输入/执行"是否成功，不必依赖肉眼观察。
