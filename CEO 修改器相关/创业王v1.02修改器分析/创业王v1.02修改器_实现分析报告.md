# 创业王 v1.02 修改器 —— 实现方式分析报告

> 分析对象：`创业王v1.02修改器.exe`（副本存于本目录 `创业王v1.02.exe`，670,208 字节，32 位 Windows）
> 分析日期：2026-09-12 · 工具：pefile + IDA Pro 9.3 (idalib) + 自制内存转储器 + Cheat Engine 脚本比对
> 输出目录：`D:\game\CEO\修改器\创业王v1.02修改器分析\`

---

## 1. 一句话结论

这个修改器是一个**内嵌了 Cheat Engine 自动汇编（AA）脚本引擎的"脚本执行器"**：程序本体加壳（ASPack），运行后在内存中解包；它通过窗口标题定位游戏进程（OpenProcess/WriteProcessMemory 均为运行期动态解析以躲避朴素查杀），内部以字符串形式**硬编码了 10 段 Cheat Engine 格式的注入脚本**（`[ENABLE]/alloc(newmem)/label/...CEO.exe+偏移`），用户按下热键后，由内置的 AA 解析器在游戏进程内 `VirtualAlloc` 一块 `newmem`、把补丁逻辑写入、再用 5 字节 `jmp` 改写 CEO.exe 的固定代码偏移，从而实现金钱无限、矿物改类型、强占厂房、秒建设、秒生产等功能。

## 3. 脱壳方法（不依赖脱壳工具）

ASPack 在进程启动后数十毫秒内完成自解压。因此采用"**运行后外部内存转储**"：

1. 正常启动修改器（`dump_trainer.py` 自动完成）；
2. 通过 `CreateToolhelp32Snapshot` 定位进程（含 32 位模块需 `TH32CS_SNAPMODULE|TH32CS_SNAPMODULE32`）；
3. `ReadProcessMemory` 读入整个主模块镜像（0x400000 起 0x250000 字节）——此时内存中已是**完全解包的代码 + 已解析完毕的 IAT**；
4. 用 pefile 按原节区表把内存内容写回文件 → `trainer_unpacked.exe`（2.9MB，已校验每个节区与内存一致，EP 暂置 0x401000）；
5. 遍历进程内各系统 DLL 导出表，生成 `exports_map.json`（8,550 个 导出地址→名称），扫描转储中命中这些地址的 DWORD → `iat_annotations.json`（424 个真实导入），在 IDA 中批量命名，恢复可读的反编译。

## 4. 总体实现架构

```
┌─ 修改器进程 (ASPack 解包后) ─────────────────────────────┐
│  UI 界面(勾选项: 年代/工厂/矿物类型…)                      │
│  热键处理: F1-F5, Alt+1/2/3, Ctrl+Z/X/C                   │
│            (资源中另有 Ctrl+Shift+F1-F12 等完整热键表)      │
│                                                          │
│  AA 脚本执行器 sub_401C87 ←─ 10 段内嵌 CE 格式脚本          │
│   ├─ 解析 [ENABLE]/[DISABLE]/alloc/label                  │
│   ├─ 符号解析: "CEO.exe+202E3" → 模块基址+偏移             │
│   ├─ x86 汇编器: 把 newmem 汇编为机器码                    │
│   └─ 写入游戏: OpenProcess + VirtualAllocEx               │
│                + WriteProcessMemory (5字节 jmp 钩子)       │
│                                                          │
│  API 隐藏: sub_4CED79 用加密常量(push 16012F31h 等)        │
│  动态解析 API; 明文字符串仅保留 "OpenProcess"/             │
│  "WriteProcessMemory"/"ReadProcessMemory" 供 GetProcAddress│
└──────────────────────────────────────────────────────────┘
         │ OpenProcess / WriteProcessMemory
         ▼
   CEO.exe (游戏进程, 无需游戏侧配合)
```

关键证据：

| 脚本执行入口 | `sub_401C87(上下文, "CEO.exe+202E3", "[ENABLE]…")`（0x401B19 处调用） | 每个功能一段脚本 |

## 5. 内嵌 AA 脚本与功能映射（已与游戏逆向结果交叉验证）

10 段脚本原文见 `aa_scripts/`（含 `index.json`）。钩子全部落在 CEO.exe 的 `.text`（RWX）内，与《CEO_逆向架构报告》的函数划分对应：

| 脚本 | 游戏内钩子 | 所在函数（本报告命名） | 语义 |
|---|---|---|---|
| s00 | `CEO.exe+202E3` | 0x401E70（城市/地块金钱结算） | 金钱无限：`cmp [ebp+738],0` 成立时跳过 `sub ecx,eax`（不减钱）→ **F2** |
| s01 | `CEO.exe+9E1B` | 0x409C00（玩法主更新 0x409000 簇） | `lea edi,[esi+3]; mov [CEO.exe+A7848],edi` —— 把"当前选中地块的类型字节地址"缓存到 0x4A7848 → **F3 矿物修改** |
| s02 | `CEO.exe+5CF3B` | 0x45CE50（建设菜单过滤，比对年代字段 `[eax+ecx+E0]` 与 dword_856610） | 缓存选中建筑类型指针 → 0x4A784C → **地块改建筑/年代勾选** |
| s03 | `CEO.exe+3B2D3` | 0x43B200（矿区信息界面 factinf_mine） | 缓存 `[ebx+8]`（当前厂房对象指针）→ 0x4A7840 → **F1/F4 厂房类功能的目标缓存** |
| s04 | `CEO.exe+2025F` | 0x402220（地块数组扫描，`[eax+1Ch]!=FFFF` 判归属） | 改写归属字段写入路径 → **F4 强占厂房** |
| s05 | `CEO.exe+20268` | 同上 | 同系列 |
| s06 | `CEO.exe+2026E` | 同上 | 同系列 |
| s07 | `CEO.exe+204FC` | 0x402420（建设队列扫描 `[eax+edx*2+50h]`） | → **F5 建设秒完成** |
| s08 | `CEO.exe+2790F` | 0x426AB0（生产/进度推进，0x1580 字节大函数） | `cmp [ecx+738],0 / je 原逻辑; else inc word[eax]` —— 计数 +1 → **机器秒生产**（原逻辑写 0xC3500=800000） |
| s09 | `CEO.exe+27765` | 同上（另一分支） | 同系列 |

**反复出现的 `[reg+738]`**：三个脚本都在检查某个对象 +0x738 处的标志位（0 层走"作弊路径"）。这是修改器作者在游戏内部发现的状态位（或配合脚本写入的开关），未在游戏侧进一步核实，标注为**中等置信**。

**`fullaccess(CEO.exe+A7848/A784C/A7840, 4)`**：CE AA 语法，声明这些游戏地址可写（4 字节），实际是 0x4A7840–0x4A7850 一组"选中对象指针槽"，位于 CEO.exe `.text` 末尾的未初始化区域（该游戏把代码段尾部当 BSS 用）。

**交互模式**：说明.txt 要求"先鼠标点击目标，再按热键"——因为 s01–s03 的钩子只负责把"当前选中对象"的指针缓存到 0x4A7840 槽位，热键处理函数再读取槽位、按 UI 勾选（矿物种类/建筑类型/年代）通过 WriteProcessMemory 改写游戏数据。`mouse_event` 字符串表明部分流程还会模拟点击。

## 9. 补充深挖：Ctrl+Z / X / C（快速放主管/工人/宣传车）的实现原理

> 本节为针对该三热键的专项分析（证据：`decomp/004972D9.c`、`004979DA.c`、`00497571.c`、`004961A6.c`、`00497085.c`、`0040258F.c`、`00495E87.c`、`hotkey_xrefs.txt`）。

### 9.1 热键捕获

- 修改器导入表（脱壳后重建）中含 `GetKeyState`(IAT 0x574420)、`SetWindowsHookExA`(0x5745E0)、`CallNextHookEx`(0x5745DC)、`mouse_event`(0x5745C0)、`GetForegroundWindow`(0x574638)、`PostMessageA`(0x574540)。
- `0x4EAAE0`（14.6KB）是一个**键盘/鼠标消息转发钩子回调**：按消息类型（WM_KEYDOWN=0x100/WM_KEYUP=0x101/WM_CHAR=0x102/SYSKEYDOWN/UP、鼠标滚轮 0x20A/按键 0x203-0x205）分支，用 `GetKeyState(17=VK_CONTROL)/16=Shift/18=Alt` 收集修饰键状态，经 `sub_4E4C60(2008, …)` 分发——这就是"游戏窗口在前台时热键仍有效"的来源（钩子链由 `SetWindowsHookExA` 建立，回调 0x56836D，`CallNextHookEx` 透传）。

### 9.2 三个切换处理器（已反编译）

| 热键 | 处理函数 | 界面文字 | 专属常量（伪装成 double 的偏移） |
|---|---|---|---|
| Ctrl+Z（放主管） | 0x4972D9 | `Ctrl+Z：开/关.鼠标给主管` | 4779996.0 = **0x48EFDC** |
| Ctrl+X（放工人） | 0x4979DA | `Ctrl+X：开/关.鼠标给工人` | 4779996.0 = **0x48EFDC**（与 Z 共用） |
| Ctrl+C（放宣传车） | 0x497571 | `Ctrl+C：开/关.鼠标锁宣传车` | 4965780.0 = **0x4BC594** |

每个处理器的执行序列（以 0x4972D9 为例，全部 API 经哈希混淆引擎 `sub_4CED5B/55/61/6D/73/79` 调用）：

1. `sub_4CED6D(哈希1, 哈希2, 8, -1, 文本, 0)` —— 按 UI 控件哈希设置开关文字（互斥：激活 Z 时会把 X 的文字重置为"开"状态，即三种模式互斥）。
2. `sub_4961A6(游戏句柄, &出参)` —— **读游戏内存**（RPM 封装，8.6KB 重度混淆函数）。
3. `sub_4014CE((double)读值 + 4779996.0)` —— 把"读值 + 常量偏移"的地址计算**伪装成浮点运算**（4779996.0 = 0x48EFDC，是 CEO.exe 内的目标偏移；宣传车用不同偏移 0x4BC594，这就是三种实体目标的区分点之一）。
4. `sub_497085(游戏句柄, 计算结果, 1)` —— **WriteProcessMemory 封装**，向计算出的游戏地址写 1 字节（放置对象类型/目标槽状态）。
5. `sub_40258F(&WAV指针)` —— 播放内嵌 **WAV 音效**反馈开关状态（0x57D240/0x580AF7 均为 `RIFF…WAVE` 资源，带 4 字节长度前缀；此前误判为脚本，已更正）。
6. 若切到"开"：`sub_495E87("CEO.exe", 1)` —— 把符号解析基准绑定到 CEO.exe 模块（供后续 `CEO.exe+X` 符号计算）。
7. `Sleep(50)` 循环：反复读取比较状态文字并持续重写第 4 步的值 —— **状态强制维持**，直到游戏侧生效。

### 9.3 放置动作的原理

与 F1-F5（注入 AA 代码钩子）不同，Ctrl+Z/X/C 走的是**纯数据改写**路线：

1. 按热键 → 上述处理器把游戏内部"当前放置对象类型/目标槽状态"字节改写为对应实体（主管/工人/宣传车）；
2. 玩家随后在厂房界面的空槽上点击 —— 游戏按它自己记忆中的"当前放置类型"放置实体，于是放下的是主管/工人/宣传车；
3. 这解释了说明.txt 的两个怪现象：
   - "**鼠标不显示人物/车**"：放置类型是在内存里改的，游戏没有走正常拾取流程，携带光标贴图不会切换；
   - "**游戏中左上角点一下主管，再按快捷键即可显示**"：需要让游戏 UI 重新同步内部状态。

### 9.4 与 F 系热键的机制对比

| | F1-F5 / Alt+1-3 | Ctrl+Z/X/C |
|---|---|---|
| 手段 | AA 脚本注入：游戏内 alloc newmem + 5 字节 jmp 代码钩子 | RPM 读 → 偏移计算（浮点伪装）→ WPM 写 1 字节，无代码注入 |
| 生效方式 | 持久钩子（改写游戏逻辑） | 改"当前状态值"，靠游戏自身逻辑生效 |
| 维持 | [ENABLE]/[DISABLE] 开关 | 50ms 轮询循环强制维持 |
| 反馈 | 无音效 | 内嵌 WAV 音效 + UI 文字开/关 |

*置信度：捕获链、处理器流程、RPM/WPM 封装、音效反馈为高置信（反编译直接证据）；写 1 字节的确切语义（类型码 vs 槽状态）与 0x48EFDC/0x4BC594 的精确含义为中等置信（读改写路径已证实，但写入值经过混淆引擎，未逐字节核对）。*

## 10. 补充：移植到 1.10 版游戏的可行性验证（详见 ..\v1.10移植\）

对 Steam 版 1.10（`CEO.exe` 816KB，重编译链接：.text 640KB + .data 巨型 BSS，节区 3→5，非加壳）的分析结论：

1. **修改器的静态偏移设计在 1.10 上全部失效**，且 1.10 恰好重写了大部分被钩代码（10 个钩子点中 9 个的原始指令序列在 1.10 中已不存在——字节级匹配证伪）；仅 s01（F3 矿物修改）的指令序列原样保留。
2. **方法论已验证**（端到端跑通）：钩子点用"Alt 原始字节+上下文"匹配；全局变量用"访问指令上下文 + 4 字节立即数通配"匹配；数据槽选用 1.10 .data 尾部无引用 BSS 页。
   - 已完成重定位并验证：s01 钩子 0x409E1B→**0x40A36E**；Ctrl+C 全局 0x8BC594→**0x8D6074**（`mov [0x8BC594],0` → `mov [0x8D6074],0` 指令级证据）；数据槽→0x4F7040/48/4C（0 引用）。
3. **交付**：`..\v1.10移植\loader_v110.py` —— 内存补丁加载器（启动修改器→等壳解压→打补丁），含安全策略（未移植脚本自动禁用，杜绝写错内存）；`test_loader.py` 自检全部通过；剩余 F2/F1/F4/F5/秒生产/Ctrl+Z/X 需按 README 的路线逐钩子语义重定位（1.10 改动了这些玩法代码，无法靠偏移平移）。
4. 移植包详见 `..\v1.10移植\README.md`（含 v1.02→v1.10 地址对照表与工具链说明）。
